# 사용법

## 기본 — 그냥 일을 시킨다

```
@fixy 사용자 프로필 수정 API 만들어줘
@fixy 이 컴포넌트 리렌더가 너무 많은데 최적화해줘
@fixy 결제 콜백에서 가끔 중복 처리돼 [로그 첨부]
```

`@fixy` 는 매 작업에서 다음을 한다:

1. **recall** — `fixy_recall` 로 "전에 비슷한 걸 배웠는지" 먼저 확인 (추측·재조사 최소화)
2. **레거시 존중** — 대상 프로젝트의 기존 구조·컨벤션·스타일을 파악하고 따른다
3. **구현** — 작은 단위로, 테스트·타입·빌드 초록 확인
4. **검증** — M 이상 규모면 `@fixy-reviewer` 로 독립 검증, Critical/High 는 수정 후 재검증
5. **기록** — 새로 알아낸 절차나 받은 교정을 L1 에 남김

## 시나리오

### 신규 기능
```
/fixy-feature 주문 취소 API (취소 가능 상태 검증 포함)
```
컨벤션 파악 → 구현 → 검증까지. 새로 익힌 절차는 자동 기록.

### 디버깅
```
/fixy-fix 결제 승인 후 webhook 이 가끔 두 번 와서 중복 적립됨
[스택 트레이스 / 로그 첨부]
```
재현 → 근본 원인 격리 → 최소 수정 → 검증. **재발 가능성이 있으면** 증상→원인→해결→예방 런북을 기록한다. 같은 에러가 또 오면 `fixy_recall` 로 즉시 재사용.

### 코드 리뷰
```
/fixy-review 방금 변경한 OrderService
```
`@fixy-reviewer`(읽기 전용)가 정확성·레거시 일관성·버그·보안·테스트·단순성을 심각도별로 점검. 코드는 직접 고치지 않는다.

### 불만 → 학습으로 이어지는 전형적 흐름
```
1. @fixy 목록 정렬 최신순으로 해줘
2. (fixy 가 생성일 기준으로 정렬)
3. @fixy 아니 수정일 기준이어야지        ← 'correction' 신호로 L1 자동 기록
4. (fixy 가 고치고 fixy_note 로 교훈 핀)
   … 비슷한 "정렬 기준" 교정이 더 쌓이면 …
5. /fixy-evolve   → "list-sort-convention" 스킬 생성
6. /fixy-share    → 포크 PR. 팀원도 이 스킬을 받음
```

## 커맨드 레퍼런스

| 커맨드 | 언제 쓰나 | 핵심 동작 |
|---|---|---|
| `@fixy <요청>` | 일반 개발 작업 | recall → 구현 → (검증) → 기록 |
| `/fixy-feature <설명>` | 신규 기능 | 컨벤션 준수 + 검증 |
| `/fixy-fix <에러>` | 디버깅 | 근본원인 → 수정 → 런북 기록 |
| `/fixy-review <대상>` | 변경 검증 | 독립 리뷰(읽기 전용) |
| `/fixy-status` | 현황 파악 | 레벨 파이프라인 + 권장 액션 |
| `/fixy-evolve` | 기록이 쌓였을 때 | L1 클러스터 → L2 스킬 승급 |
| `/fixy-level-up [대상]` | 스킬을 격상 | L2→L3 자동 / L3→L4/L5 제안+승인 |
| `/fixy-share [스킬]` | 팀에 공유 | 시크릿 스캔 → 포크 PR |

## 도구를 직접 부를 때

```
fixy_recall query="jwt 토큰 갱신"               # 관련 스킬 검색·재사용
fixy_note signal=insight summary="..." tags=[...] # 수동 L1 기록
fixy_status                                      # 파이프라인 현황
fixy_digest                                      # L2 승급 후보 클러스터
fixy_share skills=["..."] title="..." dryRun=true # 공유 사전 점검
```

## 자동 공유 (선택)

기본은 수동(`/fixy-share`). 세션 종료 시 자동 PR 을 원하면:

```bash
export FIXY_AUTOSHARE=1          # 또는 fixy.config.json 의 share.autoOnIdle = true
```

보수적으로 동작한다: `minLevelToShare`(기본 2) 이상 + 미커밋 스킬만 + 시크릿 스캔 통과 + 디바운스(90초). 깜짝 PR 을 막기 위해 대상 저장소가 설정돼 있어야 한다.

## FAQ

**Q. 내 개인 기록(L1)이 팀에 새나가나?**
아니다. `memory/episodes.jsonl` 은 `.gitignore` 라 공유되지 않는다. 공유는 L2+ 스킬·규칙뿐이며, 매번 시크릿 스캔을 거친다.

**Q. 스킬이 너무 많아지면 지저분해지지 않나?**
레벨이 자연 필터다. 자주 안 쓰이는 L2 는 L3 로 올라가지 못한다. `/fixy-status` 로 노이즈를 확인하고, 불필요한 스킬 디렉토리는 직접 지우면 된다.

**Q. fixy 가 같은 지적을 또 받는다.**
새 작업 전 `fixy_recall` 이 먼저 도는지 확인하라(에이전트 프롬프트에 강제돼 있다). 관련 스킬이 아직 없다면, 교정을 몇 번 더 받아 L1 이 쌓인 뒤 `/fixy-evolve` 로 스킬화하라.

**Q. 모델은 무엇을 쓰나?**
에이전트는 모델을 고정하지 않아 각자 opencode 기본 모델을 쓴다(팀 이식성). 고정하려면 `agents/fixy.md` 의 frontmatter 에 `model:` 추가.

**Q. 다른 opencode 플러그인과 충돌하나?**
아니다. 설치는 추가 링크만 하고 기존 설정을 안 건드린다. 이름이 `fixy-*` 라 충돌도 없다.

**Q. 팀원과 어떻게 나누나?**
각자 이 레포를 fork → install → 자기 포크로 학습물 PR(`fixy/skill-*`). 좋은 스킬은 팀 원본(upstream)으로 다시 PR 해 모두가 `update.sh` 로 받는다. (자세한 레벨 흐름: [levels.md](levels.md))

**Q. 학습을 잠깐 끄고 싶다.**
`FIXY_RECORD=0` 으로 L1 기록을 끈다. 자동 공유는 기본 OFF 다.
