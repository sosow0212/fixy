# 체계적 디버깅

## 언제 쓰는가
에러·예외·예상과 다른 동작·간헐적 장애를 만났을 때.

## 핵심 원칙
**추측하지 말고 관찰하라.** 고치기 전에 원인을 증명한다.

## 절차
1. **재현**: 가장 작고 신뢰성 있는 재현 경로를 만든다. 재현 안 되면 환경 차이(버전·env·데이터·시간·동시성)를 의심한다.
2. **증상 정밀화**: 정확한 에러 메시지·스택 트레이스·실패 입력·기대 vs 실제를 적는다.
3. **범위 좁히기**: 이분 탐색 — 동작하는 지점과 깨지는 지점 사이를 절반씩 좁힌다(로그·`git bisect`·주석 처리).
4. **가설→검증**: 한 번에 하나의 가설. 로그/디버거/단언으로 증명하거나 기각한다. 여러 변수를 동시에 바꾸지 않는다.
5. **근본 원인 확정**: "왜?"를 5번 — 표면 증상이 아니라 진짜 원인까지.
6. **최소 수정**: 원인만 정확히 고친다. 김에 다른 것 건드리지 않는다.
7. **검증**: 재현 경로가 사라졌는지 + 회귀 테스트 추가.
8. **예방**: 같은 류를 막을 가드(검증·타입·테스트·문서)를 남긴다.

## 자주 놓치는 원인
- 누락된 `await`/비동기 경쟁, off-by-one, null/undefined 경계
- 캐시·빌드 산출물 stale, 환경변수 차이, 타임존/로케일
- 잘못된 에러 삼킴(`catch {}`), 로그 부재

## 기록
재발 가능성이 있으면 `fixy_note`(insight) 로 **증상→원인→해결→예방** 런북을 남긴다. 같은 에러가 또 오면 `fixy_recall` 로 즉시 재사용.
